## Services

### AttendeeScheduling

AttendeeScheduling is the attendee-sent half of iTIP, RFC 5546: REPLY, REFRESH and COUNTER. See organiser_service.proto for the organiser-sent half, and for why METHOD is modelled as the RPC and every method is long-running.

### OrganiserScheduling

OrganiserScheduling is the organiser-sent half of iTIP, RFC 5546: the protocol for agreeing a calendar entry between an organiser and its attendees. See attendee_service.proto for the attendee-sent half.  **METHOD is the RPC, not a field.** RFC 5546 works by putting a METHOD property on an iCalendar object, which turns that object into a message envelope. Modelling it that way here would have given Event a `method` field and stopped it being a calendar entry -- an event would then mean something different depending on how it arrived. Each METHOD is an operation instead, which is also what makes the organiser/attendee split expressible as two services rather than one with mixed permissions.  **Who may send what**, section 3.2 <https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2>: an organiser sends PUBLISH, REQUEST, ADD, CANCEL and DECLINECOUNTER -- this service. An attendee sends REPLY, REFRESH and COUNTER -- AttendeeScheduling. That split is a property of the protocol, not of this API, and a server must enforce it: an attendee who can cancel other people's meetings is a scheduling system with no organiser.  **Every method is long-running.** A scheduling message fans out to every attendee over transports this API does not own, so delivery cannot be reported synchronously. Each operation resolves to a response carrying one google.rpc.Status per recipient: one bad address must not fail the other nine invitations. Only the methods that can change a scheduling-significant property also report SEQUENCE -- see organiser_messages.proto for which.

### PublishEventRequest

Request message for Scheduling.PublishEvent, RFC 5546 section 3.2.1 <https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.1>.  This file and attendee_messages.proto together hold every scheduling request and response: this one for the organiser-sent methods -- PUBLISH, REQUEST, CANCEL, DECLINECOUNTER -- the other for REPLY, REFRESH, COUNTER.  Every scheduling method names the event it concerns by resource name, not by the Event message itself: the event lives in another proto package and AIP-215 <https://aip.dev/215> permits no cross-package message reference. It is also the better contract -- the stored event is the source of truth, so a caller cannot send an invitation describing something the calendar does not hold.

### CalendarTime

CalendarTime is an iCalendar DATE or DATE-TIME value, RFC 5545 sections 3.3.4 <https://www.rfc-editor.org/rfc/rfc5545.html#section-3.3.4> and 3.3.5 <https://www.rfc-editor.org/rfc/rfc5545.html#section-3.3.5>.  A copy of the message in protobuf.rfc5545.event.v1, not a reference to it: AIP-215 <https://aip.dev/215> permits no cross-package message reference. This is the fourth package to carry it, after event, todo and journal -- see the AIP-215 duplication tax in plan/00-sequence.md for the alternative, a single rfc5545 package that would remove the copies at the cost of per-resource versioning.  Reference: RFC 5545 "Internet Calendaring and Scheduling Core Object Specification (iCalendar)", section 3.3.5. https://www.rfc-editor.org/rfc/rfc5545.html#section-3.3.5
