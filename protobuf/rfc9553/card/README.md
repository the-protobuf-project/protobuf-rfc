## Services

### Cards

Cards manages contacts in the canonical JSContact model.  **This is where contact data lives.** Under rule 14 the newest published RFC in a lineage is the storage form, so a contact saved through protobuf.rfc6350.vcard.v1's Vcards service is converted here and stored as a Card; reading it back through that service converts it out again, per RFC 9555 <https://www.rfc-editor.org/rfc/rfc9555.html> as updated by RFC 9982 <https://www.rfc-editor.org/rfc/rfc9982.html>.  That is the designed behaviour, not a lossy accident, and it is stated here rather than left for a consumer to discover: **a vCard written through the legacy API reads back as a vCard rendered from a Card, not as the bytes that were sent.** Elements neither model shares survive in `jscontact_props` (RFC 9555 section 3 <https://www.rfc-editor.org/rfc/rfc9555.html#section-3>'s `vCardProps`), so the round trip keeps the data even where it cannot keep the encoding.  These are the AIP-131..135 standard methods and nothing else. Serialising a Card to `application/jscontact+json` is not a Card-specific concern -- see protobuf.shared.interchange.v1.Interchange, which does it for any resource type.

### Address

Address is one entry of the Card "addresses" property, RFC 9553 section 2.5.1.1 <https://www.rfc-editor.org/rfc/rfc9553.html#section-2.5.1.1>.  Componentised the same way Name is, and for the same reason: RFC 6350 section 6.3.1 <https://www.rfc-editor.org/rfc/rfc6350.html#section-6.3.1>'s ADR is positional, so an address whose parts do not map onto its seven slots loses them. RFC 9554 later back-ported these components into vCard, which is what makes the conversion in RFC 9555 lossless in both directions.  This is also why google.type.PostalAddress was rejected for this schema -- see docs/adding-data.md. That type is address_lines plus a region, and cannot say which line is a floor and which is a landmark. ### Card

Card is the JSContact Card object, RFC 9553 <https://www.rfc-editor.org/rfc/rfc9553.html> as amended by RFC 9982 <https://www.rfc-editor.org/rfc/rfc9982.html>.  **The canonical contact model** under rule 14: what this schema stores. protobuf.rfc6350.vcard.v1 remains a first-class package with its own CRUD, but it is the legacy representation -- a vCard saved through that API is converted here for storage and converted back on read, per RFC 9555.  Most multi-valued properties are **maps keyed by a stable id**, not lists. That is section 1.4.1's `Id` type and it is load-bearing: the key must survive across versions of the same Card, because localizations and patches address individual entries by it. A list would renumber on every edit and break both.  RFC 9982 makes `jscontact_uid` optional, where RFC 9553 required it -- the later reading is the one implemented, because auto-generating an ephemeral uid during vCard conversion is exactly what 9982 set out to stop. ### Name

Name is the Card "name" property, RFC 9553 section 2.2.1.1 <https://www.rfc-editor.org/rfc/rfc9553.html#section-2.2.1.1>.  The structural difference from vCard is the point of JSContact. RFC 6350 section 6.2.2 <https://www.rfc-editor.org/rfc/rfc6350.html#section-6.2.2>'s N is five positional components in a fixed order, so a name that does not fit that order cannot be expressed. Here a name is an *ordered list of typed components*, so "given surname2 surname" is as representable as "surname, given" -- and `is_ordered` says whether the order given is meaningful or merely incidental.  Reference: RFC 9553 "JSContact: A JSON Representation of Contact Data", section 2.2.1.1. https://www.rfc-editor.org/rfc/rfc9553.html#section-2.2.1.1

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `components` | `repeated NameComponent` | `OPTIONAL` | The components in the order they should be read. |
| `is_ordered` | `bool` | `OPTIONAL` | Whether `components` is in a meaningful order, section 2.2.1.1 <https://www.rfc-editor.org/rfc/rfc9553.html#section-2.2.1.1>. False, the default, means the order carries no information and a client should assemble the name by its own convention. |
| `default_separator` | `string` | `OPTIONAL` | The separator to put between components when none is given explicitly, section 2.2.1.1 <https://www.rfc-editor.org/rfc/rfc9553.html#section-2.2.1.1>. Usually a space. |
| `display_name` | `string` | `OPTIONAL` | The whole name as a single string, section 2.2.1.1 <https://www.rfc-editor.org/rfc/rfc9553.html#section-2.2.1.1>. This is vCard's FN (RFC 6350 section 6.2.1 <https://www.rfc-editor.org/rfc/rfc6350.html#section-6.2.1>), and the two convert directly.  Named `display_name`, not the RFC's `full`: AIP-122 <https://aip.dev/122> bans the `_name` suffix outside a short allowlist that `display_name` is on, and a bare `full` names no thing. It also matches what the vCard package calls FN, which is the property this converts to. |
| `phonetic_script` | `string` | `OPTIONAL` | The script the phonetic components are written in, as an ISO 15924 four-letter code, section 2.2.1.1 <https://www.rfc-editor.org/rfc/rfc9553.html#section-2.2.1.1>. |
| `phonetic_system` | `PhoneticSystem` | `OPTIONAL` | The notation the phonetic components use, section 2.2.1.1 <https://www.rfc-editor.org/rfc/rfc9553.html#section-2.2.1.1>. |

### Speech

Speech is the Card "speakToAs" property, RFC 9553 section 2.2.4 <https://www.rfc-editor.org/rfc/rfc9553.html#section-2.2.4>.  How to refer to the contact in speech and prose. Named `Speech` rather than the RFC's `SpeakToAs`: AIP-140 <https://aip.dev/140> bans prepositions in field names, so the field cannot be `speak_to_as`, and a message whose name does not match its field reads worse than one renamed honestly.  Section 2.2.4 is explicit that grammatical gender "does not allow inferring the gender identities or assigned sex of the contact" -- it is a property of the language being written, and `pronouns` is the separate, self-reported thing. The two are deliberately distinct fields here for that reason.  Reference: RFC 9553 "JSContact: A JSON Representation of Contact Data", section 2.2.4. https://www.rfc-editor.org/rfc/rfc9553.html#section-2.2.4

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `grammatical_gender` | `GrammaticalGender` | `OPTIONAL` | The grammatical gender to use in prose about the contact, section 2.2.4 <https://www.rfc-editor.org/rfc/rfc9553.html#section-2.2.4>. A property of the language, not of the person. |
