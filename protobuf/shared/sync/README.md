## Services

### Sync

Sync reports what changed in a collection since a caller last asked.  One generic service keyed on `resource_type`, per rule 7: synchronization applies to resources in general, so it is not a method added to each of the fourteen resource services. `Interchange` is the same shape for the same reason.  What this follows, and what it is not.  The model is RFC 6578 <https://www.rfc-editor.org/rfc/rfc6578.html>: an opaque token marks a position in a change history, the client returns it, and the server reports the members that moved. CalDAV and CardDAV both use it, so a consumer bridging either protocol onto this schema meets a mechanism it already implements.  This is not a WebDAV implementation. RFC 6578 defines an XML REPORT over HTTP with `DAV:sync-token`, `DAV:sync-level` and a 507 status; this is an AIP-shaped RPC that borrows the mechanism. Where the two differ the comments say which choice was made and why. `sync-level` in particular has no equivalent: WebDAV collections nest arbitrarily and these do not, so depth is answered by `parent` instead.  Why not streaming.  A change feed invites a server-streaming RPC, and this is deliberately unary. A poll returning a token is resumable across a dropped connection, a restarted process and a client that was offline for a week; a stream is none of those without rebuilding exactly this token underneath it. The intended shape is a notification transport -- a message bus, a webhook, anything that says "something moved" -- waking a client that then calls this to find out what. That keeps delivery and state in separate pieces, and only one of them has to be durable.  What it does not do.  Conflict resolution. Two clients writing the same resource is settled by `etag` and AIP-154's conditional update, which every resource already carries; this service reports what happened and takes no position on what should have. Nor does it carry resource bodies -- see Change.

## Messages

### Change

Change is one resource whose state moved, RFC 6578 sections 3.5.1 <https://www.rfc-editor.org/rfc/rfc6578.html#section-3.5.1> and 3.5.2 <https://www.rfc-editor.org/rfc/rfc6578.html#section-3.5.2>.  It carries a resource **name**, not the resource. Rule 4 permits no cross-package message reference, so a generic service cannot name `protobuf.rfc9553.card.v1.Card` -- and section 3.5.1's own model is a list of member URLs rather than their bodies, so following the RFC and following rule 4 point the same way here. A client re-fetches what it cares about.  Reference: RFC 6578 "Collection Synchronization for WebDAV", section 3.5. https://www.rfc-editor.org/rfc/rfc6578.html#section-3.5

### SyncResourcesRequest

Request message for Sync.SyncResources, RFC 6578 section 3.2 <https://www.rfc-editor.org/rfc/rfc6578.html#section-3.2>.

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `resource_type` | `string` | `REQUIRED` | Resource type to synchronize, e.g. "protobufrfc.dev/Card".  The string each resource declares in `google.api.resource`, which is what rule 7 keys a generic service on. Discover the set through protobuf.shared.interchange.v1.Interchange.ListCodecs, which is keyed the same way. |
| `parent` | `string` | `OPTIONAL` | Collection to synchronize within, for a resource whose name is nested, e.g. "calendars/c1" for events. Empty for a top-level collection. |
| `sync_token` | `string` | `OPTIONAL` | Opaque token from a previous SyncResourcesResponse.next_sync_token.  Empty means initial synchronization, and section 3.4 is specific about what that returns: every member, and no removals. A client with no prior state has nothing to be told is gone.  Not a `page_token`. AIP-158's token is a position in a snapshot and pages through what exists; this is a position in a change history and reports what moved. The difference is removals, which pagination cannot express. A caller that wants the current collection should call the resource's own List method instead. |
| `max_changes` | `int32` | `OPTIONAL` | Maximum changes to return. Defaults to 100, capped at 1000.  Named `max_changes` rather than `page_size` deliberately: `page_size` brings AIP-158's pagination contract with it, including a `page_token` that would be a second cursor beside `sync_token`. Section 3.6 makes the sync token the cursor, so there is only one.  Section 3.6 lets a server truncate regardless, so a caller must handle a short page whatever it asks for. |

### SyncResourcesResponse

Response message for Sync.SyncResources, RFC 6578 section 3.2 <https://www.rfc-editor.org/rfc/rfc6578.html#section-3.2>.

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `changes` | `repeated Change` | - | The changes since the request's token, section 3.5 <https://www.rfc-editor.org/rfc/rfc6578.html#section-3.5>.  A resource that changed several times appears once: the client re-fetches current state, so intermediate values are not useful and section 3.5 does not report them. |
| `next_sync_token` | `string` | - | Token to pass to the next call.  Always set, including when `changes` is empty -- an empty response with a fresh token is how a caller learns it is up to date, and discarding the token would force a full resynchronization next time.  Section 3.6: when a response is truncated this token represents the partial state, so passing it back continues through the remaining changes rather than repeating them. That makes the token do double duty as a paging cursor, which is why there is no separate `next_page_token`. |
| `has_more` | `bool` | - | Whether more changes are waiting, section 3.6 <https://www.rfc-editor.org/rfc/rfc6578.html#section-3.6>.  A caller draining a backlog should keep calling while this is true rather than waiting for the next notification, and should not infer "done" from a short page: a server may truncate below the requested size. |
| `token_expired` | `bool` | - | Whether the request's token was rejected and this response is a fresh initial synchronization, section 3.2 <https://www.rfc-editor.org/rfc/rfc6578.html#section-3.2>.  A server may invalidate tokens -- section 3.2 names limited change history as the reason, and requires it happen "only when absolutely necessary". When it does, `changes` holds every member as if the token had been empty, and **a client MUST discard local state it believed was current** rather than merging, because removals it missed are not in this response.  A field rather than an error: the caller gets the data it needs in the same round trip, where FAILED_PRECONDITION would make it ask twice for something the server already knew it had to send. |

## Enums

### ChangeKind

ChangeKind is what happened to a resource, RFC 6578 section 3.5 <https://www.rfc-editor.org/rfc/rfc6578.html#section-3.5>.  Two values, not three. Section 3.5.1 reports a newly created member as *changed*, not as a creation of its own: "A member URL MUST be reported as changed if it has been newly mapped as a member of the target collection". A CREATED value would be this schema inventing a distinction the specification declines to make, and a client that re-fetches on either gains nothing from telling them apart.  Reference: RFC 6578 "Collection Synchronization for WebDAV", section 3.5. https://www.rfc-editor.org/rfc/rfc6578.html#section-3.5

| Value | Number | Description |

| `CHANGE_KIND_UNSPECIFIED` | 0 | Not specified. Not a value a server may send. |
