## Services

### Search

Search finds resources across types by free text.  One generic service keyed on `resource_type`, per rule 7. Searching applies to resources in general, and a per-resource search method would give a caller no way to ask one question of a Card and an Event at once -- which is the only thing this offers that AIP-160 filtering on each List method does not.  When to use which, since the two overlap:    - Narrowing one known collection by a known field is List with a filter.     `ListCards(filter: 'keywords:"vip"')` is exact, needs no index, and     returns the resources themselves.   - Asking one question of several types, in words rather than field     comparisons, is this. It needs an index and returns names.  No RFC behind it, which rule 5 requires be said plainly: this is a native capability living in `shared/` because a search surface is something an API of this shape is expected to have, not because the IETF specified one.  What the schema does not decide.  An index. This repository defines no server, and search is the one capability here that cannot be answered from the resources alone -- an implementer needs something maintaining an inverted index, and its freshness is theirs to state. Two consequences fall out of that and are worth a caller knowing: results may lag writes, and `total_size` may be absent. Returning names rather than resources makes the first survivable, because a re-fetch reads current state whatever the index believed.  Ranking. `score` has no defined scale and is comparable only within one response; nothing here says what makes one match better than another.

### SearchResult

SearchResult is one match.  It carries a resource **name**, not the resource: rule 4 permits no cross-package message reference, so a generic service cannot name `protobuf.rfc9553.card.v1.Card`. The caller re-fetches what it wants to display, which also sidesteps an index serving a stale copy of a resource that has since changed.

| Field | Type | Behavior | Description |
| --- | --- | --- | --- |
| `resource` | `string` | `REQUIRED` | Resource name, e.g. "cards/2f1a".  Named `resource` and not `name`: a field called `name` makes api-linter read the enclosing message as a resource and demand a `google.api.resource` annotation, which a search hit is not. Rule 10. |
| `resource_type` | `string` | `REQUIRED` | The matched resource's type, e.g. "protobufrfc.dev/Card". Present so a caller can route the re-fetch without parsing the name. |
| `score` | `double` | `OPTIONAL` | Relevance, higher is better.  Comparable only within one response. Scores from different queries, or from the same query against a re-indexed corpus, mean nothing next to each other, and nothing here defines a scale. |
| `snippet` | `string` | `OPTIONAL` | A fragment of the matching text, for display. May be empty, and carries no markup: highlighting is the caller's to apply. |
